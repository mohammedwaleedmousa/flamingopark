# تقرير فحص أمان ووظائف صفحات السايدبار

التاريخ: 2026-08-16  
النطاق: الصفحات التي يستدعيها سايدبار الأدمن أو سايدبار العميل فقط، مع التدفقات اللازمة لإتمام وظائفها مثل إنشاء الطلب. لم تُفحص الصفحات المخفية الأخرى فحصاً وظيفياً كاملاً.

## الخلاصة التنفيذية

- تم استخراج 35 مساراً يستدعيها سايدبار الأدمن و13 مساراً يستدعيها سايدبار العميل، وجميعها تملك Routes فعلية داخل التطبيق.
- تم تحويل دخول العميل إلى رقم جوال يمني موحّد بصيغة `+9677XXXXXXXX` مع رمز سري رقمي من 6 إلى 12 رقماً، ومنع الرموز الضعيفة والمتسلسلة والمتكررة.
- أصبحت جلسة العميل معتمدة على Supabase Auth والتحقق من المستخدم لدى الخادم؛ بيانات `localStorage` مجرد Cache وليست دليلاً على الهوية.
- تم نقل تسعير الطلب وإنشائه إلى الخادم، وربط الطلبات والفواتير والعناوين والمفضلة والإشعارات بهوية Auth الموثقة.
- عُزل حقل تكلفة المنتج `cost_price` عن المتجر، ونُقلت قراءته إلى RPC تتحقق من دور الأدمن.
- نُقل استقبال التحليلات والتقييمات إلى Edge Functions تتحقق من المدخلات والهوية وتطبق Rate limit.
- وُحّد عرض السعر في واجهة العميل على نظام العملات؛ العملة الافتراضية للمنتجات هي الريال السعودي `ر.س`.
- أزيلت مكتبة `xlsx` غير المستخدمة والمعرضة، ورُقّيت `react-router-dom` إلى `7.18.2` وثُبتت نسخ آمنة من `dompurify` و`nanoid`؛ تدقيق حزم الإنتاج الآن يعرض صفراً من الثغرات المعروفة.
- أضيف مسار `/curated` الذي كانت تستدعيه الرئيسية، وصُحح رابط العروض إلى `/seasonal-offers`، وأزيل تكرار مسارات أقسام الماركات.
- عُطلت Routes المؤجلة غير الموجودة في السايدبار (`/new-season` و`/my-shipments` و`/reset-password` و`/admin/catalog-workflow` و`/admin/countries`) مع إبقاء ملفاتها المصدرية لمرحلة لاحقة.
- تم تضييق سياسات RLS والتخزين وصلاحيات دوال `SECURITY DEFINER`، وإزالة رموز التتبع النصية من قاعدة البيانات بعد تحويلها إلى Hash.
- أضيف GitHub Actions لتشغيل TypeScript وESLint لمسارات الإطلاق واختبارات الأمان وتدقيق الحزم والبناء وفحص Edge Functions على كل Pull Request.
- لم تُطبق أي Migration أو Edge Function على مشروع الإنتاج أثناء الفحص. التغييرات موجودة في مسودة Pull Request وتحتاج اختبار Staging قبل الدمج والنشر.

| العمليات | `/admin/delivery`، `/admin/cod-regions`، `/admin/reviews` | جميع Routes موجودة | التوصيل وCOD للأدمن؛ إرسال التقييم عبر خادم ويرتبط بحساب العميل ويخضع للحد |

## تغطية صفحات العميل

| المجموعة | المسارات المستدعاة من السايدبار | نتيجة الوظائف | نتيجة الأمان |
|---|---|---|---|
| الدخول | `/auth` | رقم يمني + رمز سري، تسجيل ودخول وضيف | Auth حقيقي، Rate limit لتهيئة الحساب، منع الرموز الضعيفة، لا توجد كلمة مرور أو Hash في `public` |
| التسوق | `/home`، `/categories`، `/products`، `/seasonal-offers`، `/new-arrivals`، `/best-sellers` | Routes موجودة والبناء ناجح، والسعر الافتراضي يظهر `ر.س` | العميل يقرأ المنتجات النشطة دون `cost_price` |
| السلة | `/cart` | Route موجود؛ تدفق Checkout المرتبط به يبني بنجاح، والعملة موحدة مع بقية المتجر | السعر والخصم والتوصيل والقسيمة يعاد حسابها في الخادم ولا تُقبل إجماليات العميل |
| الحساب | `/account` | تحميل وتحديث الملف والعناوين والطلبات والفواتير مربوط بالمستخدم | الهاتف والهوية غير قابلين للتبديل من العميل، وصورة الحساب محصورة في مسار المستخدم ونوع/حجم محددين |
| المفضلة | `/favorites` | Route ومزامنة موجودان | Trigger وRLS يربطان السجل تلقائياً بـ `auth.uid()` |
| الإشعارات | `/notifications` | Route موجود وإظهار غير المقروء يعمل | قراءة إشعارات المستخدم والبث فقط؛ تعديل العميل محصور بحالة القراءة |
| معلومات المتجر | `/store-info`، `/qr-code` | Routes موجودة | محتوى عام مقصود ولا يحتوي مفاتيح سرية بحسب المفاتيح الموجودة حالياً |

حالة الضيف لم تعد تُعامل كحساب مسجل في السايدبار؛ يظهر له زر «تسجيل الدخول» بدلاً من «تسجيل الخروج».

## الإصلاحات الأمنية المنفذة في مسودة التغيير

1. **هوية العميل**
   - استخدام Supabase Auth برقم الهاتف والرمز السري.
   - منع التسجيل المجهول والعام خارج وظيفة التهيئة المحمية.
   - ترحيل حسابات العملاء القديمة بعد التحقق من صيغة الهاتف وHash من نوع bcrypt، مع نقل بيانات الاعتماد إلى Schema خاص.
   - ربط صف `customers` بـ `user_id` فريد والتحقق من الجلسة عبر الخادم.

2. **الطلبات والتتبع**
   - وظيفة `create-order` لا تقبل سعر المنتج أو الإجماليات أو تكلفة التوصيل من المتصفح.
   - الخادم يعيد جلب المنتجات والإضافات والتوصيل والقسائم وأسعار العملات ويحسب Snapshot الطلب.
   - محدد معدل حسب بصمة الطلب ورقم الهاتف، وحد لحجم Body وعدد العناصر وأطوال النصوص.
   - مالك الطلب والأدمن يقرآن الطلب من خلال الهوية؛ الضيف يحتاج رمز تتبع عشوائياً ويُخزن Hash فقط.

3. **الفواتير والملفات**
   - Bucket الفواتير خاص، والتحميل PDF فقط حتى 6MB مع فحص توقيع الملف.
   - الوصول عبر رابط موقّع قصير المدة بعد تحقق المالك/الأدمن/رمز الضيف.
   - Bucket الرفع محدد الحجم والأنواع، وصورة العميل محصورة بمساره.

4. **قاعدة البيانات**
   - سياسات RLS للطلبات والعملاء والعناوين والمفضلة والإشعارات والأرشيف.
   - تقييد تنفيذ دوال `SECURITY DEFINER` افتراضياً ثم إعادة منح الدوال التي تمت مراجعتها فقط.
   - إزالة `TRUNCATE` و`REFERENCES` و`TRIGGER` من أدوار المتصفح.
   - حماية الحقول الثابتة للملف والإشعارات بواسطة Triggers.

5. **تكلفة المنتجات والتحليلات والتقييمات**
   - سحب SELECT على `cost_price` من أدوار المتصفح ومنح بقية أعمدة الكتالوج فقط.
   - جلب التكلفة في صفحات الأدمن عبر `get_admin_product_costs` بعد التحقق من الدور.
   - سحب INSERT العام من `analytics_events` وإرسال أحداث العملاء المسجلين عبر `analytics-event` مع تحقق JWT في البوابة وداخل الوظيفة وحدود النوع والحجم والمعدل.
   - إلغاء سياسة إدخال `product_reviews` العامة وربط التقييم بـ`user_id` و`customer_id` ومنع أكثر من تقييم للمنتج نفسه.
   - رفع صور التقييم بروابط Upload موقعة ومسار يخص المستخدم والمنتج، ثم مراجعة التقييم قبل ظهوره.

الصفحات غير الموجودة في السايدبار، باستثناء التدفقات اللازمة للطلب، مؤجلة حسب طلب صاحب المشروع.

## التحقق المنفذ

- `npm run typecheck`: ناجح بلا أخطاء.
- `npm run lint:launch`: ناجح لملفات الهوية والطلب والعملات ومسارات العميل والسايد بار والمسارات الإدارية الحرجة المحددة.
- `npm run build`: ناجح، 5435 module تم تحويلها.
- `npm run test:security`: ناجح، 15 من 15 اختباراً.
- `npm run audit:prod`: ناجح، صفر ثغرات معروفة في اعتماديات الإنتاج.
- `deno check` لوظائف Edge الخمس: ناجح.
- تحليل Migration: 184 عبارة SQL قابلة للتحليل.
- `git diff --check`: ناجح.
- فحص قاعدة الإنتاج كان للقراءة فقط؛ لم تُغير بيانات أو إعدادات أو Functions.

## بوابة النشر

لا يُنصح بدمج التغيير أو تشغيل `supabase db push` مباشرة على الإنتاج بسبب وجود Drift بين تاريخ Migrations في المستودع والإنتاج. الترتيب الآمن:

1. نسخة احتياطية وقاعدة Staging/فرع Supabase.
2. تطبيق Migration الجديدة وفحص Advisors.
3. نشر `customer-auth-bootstrap` و`create-order` و`invoice-access`، ثم نشر `analytics-event` و`submit-review` مع إبقاء تحقق JWT الافتراضي مفعلاً لهما.
4. تشغيل سيناريوهات دخول عميل قديم وجديد، ضيف، إنشاء طلب، تتبع، حساب، مفضلة، إشعار، فاتورة، Analytics وتقييم بصورة.
5. نشر واجهة الويب، ثم مراقبة Auth/API/Edge logs قبل الدمج النهائي.
